# The wolf token inventory fackr's highlighter is generated from

fackr has a hand-written char-scanning tokenizer with a per-language table
(`src/syntax/languages.rs`). `wolf_def()` is the output of this document, not
of anyone's memory of the language — which is what lets ls05's grammar-drift
check cover a table that lives in another repo.

**Source of truth**, both at pin `67c977f`:

- `vendor/upstream/spec/grammar.ebnf` — the extracted grammar, for keywords,
  punctuation and the assignment operators.
- `upstream/spec/01-grammar.md` §1.2, §1.5, §3.2, §6 — for comments, string
  forms, and the operator climb.

## The gap this document records

`grammar.ebnf` is generated by `wolf xtask spec-extract`, and the extraction
**elides the precedence climb**: the file itself says
`/* …tiers 5–13 by the table; extraction includes the full climb… */`, and the
quoted terminals it does carry are missing `==` `!=` `<` `>` `<=` `>=` `<=>`
`&&` `||` `<<` `>>` `/` `&`. Only `spec/01-grammar.md` §3.2 has them.

A drift check reading `grammar.ebnf` alone therefore **cannot see an operator
change**, and would pass a table that had gone stale. Two ways out, both
upstream: teach `spec-extract` to emit the climb, or have the drift check read
§3.2's table directly. Recorded here so ls05 inherits the problem rather than
rediscovering it.

## Keywords — the closed set of 50 `[gram.inv.kw]`

Verbatim from `reserved_kw`, and the count is the spec's own checksum:

```
as asm assume borrow break comptime const continue copy defer distinct dyn
else enum errdefer export extern false fn for freeze handle if impl import in
let loop match move mut proc pub region return scope select shared spawn
struct take trait true type unsafe use var weak when while
```

**Contextual keywords are excluded** (`[gram.inv.ctx]`): `c`, `rc`, `pool`,
`from`, `timeout`, `noalias`, `pkg`, `reg`, `self`, and the asm operand
directions. Each is an ordinary identifier everywhere except one position, and
a regex tokenizer cannot see position. Painting `from` and `timeout` as
keywords would be wrong far more often than right — they are exactly the good
identifiers the spec declined to reserve.

## Types

```
bool int str Self
```

Small, and deliberately so. Wolf has **no fixed-width scalar inventory in the
pin**: `i32`/`u64`/`f64` and friends appear in neither `grammar.ebnf` nor any
`spec/*.md` at `67c977f`. Every name above is one the pinned spec or corpus
actually contains (`int` ×35, `str` ×20, `bool` in `02-memory-model.md`'s
restricted-value table, `Self` in the corpus). Guessing the rest would be
inventing language surface in an editor table, which is how a highlighter ends
up teaching people a language that does not exist.

`type` and `region` are *also* type-level (`type ::= … | 'type' | 'region'`)
but they are reserved keywords, so they are already in the set above.

## Operators — §3.2's climb, longest match first

```
<=>  <<=  >>=  ..=
==  !=  <=  >=  &&  ||  <<  >>  ..  ->  =>  +=  -=  *=  /=  %=  &=  |=  ^=
+  -  *  /  %  &  |  ^  !  <  >  =  ?  @
```

Order matters: fackr's `try_parse_operator` returns the **first** entry that
matches, so a three-character operator must precede its two-character prefix or
`<=>` lexes as `<=` then `>`.

`^` carries two jobs (bitwise xor at tier 9, and D25's from-end index marker
`s[^1]`) and `!` three (prefix not, the `!T` error-union type, and `!=`) — a
tokenizer that only colours them does not have to tell them apart.

## Punctuation

```
{ } ( ) [ ] , . : ;
```

`#[` opens an attribute; fackr's attribute scanner is hardcoded to Rust
(`lang.name == "Rust"`), so wolf attributes colour as `#` + punctuation for
now. Not worth a special case until someone minds.

## The rest of the table

| field | value | why |
|-------|-------|-----|
| `line_comment` | `"//"` | `[gram.lex.comment]`; covers `///` and `//!` |
| `block_comment_start/end` | `None` | **wolf has no block comments** — "nesting arguments lose to simplicity + lexer speed". A `/*` is two operator tokens, and there is a test for it |
| `string_delimiters` | `['"']` | `[gram.lex.str]`. There is no character literal |
| `multiline_strings` | `true` | `"""` with column-driven dedent `[gram.lex.str.multi]` |
| `case_sensitive` | `true` | |
| `has_preprocessor` | `false` | |

## What the table cannot express

fackr's tokenizer is regex-shaped and single-pass, so three real parts of wolf
lexical structure are out of reach. None is a reason to add a shim — they are
the argument for semantic tokens whenever the compiler ships them (post-v1):

1. **F-string interpolation.** Every string literal is an f-string, and `{x}`
   re-enters token mode inside it (`[gram.lex.str]`). fackr colours the whole
   literal as a string, so the expression inside an interpolation is not
   highlighted. `{{`/`}}` escapes are likewise invisible.
2. **Generalized literals.** `re"[a-z]+"` and `path"/etc/hosts"` are an
   identifier fused to a string with no space between; the prefix colours as
   an identifier, which is not wrong, just not special.
3. **Raw strings.** `r#"…"#` fences balance by count. The `r` colours as an
   identifier and the body as a string only by luck of the delimiters.
