# The wolf token inventory `syntax/wolf.vim` is generated from

`syntax/wolf.vim` is the output of this document, not of anyone's memory of the
language. It is the third such table in this repo — `clients/fackr/inventory.md`
(Rust) and `clients/facsimile/inventory.md` (Fortran) record the same inventory
in different target languages — and that repetition is the point: three
independently-written tables from one pinned grammar cross-check the
extraction, and a drift in one is a drift in all three.

Unlike those two, this one has a machine behind it. `cargo xtask nvim-check`
re-derives the keyword set from `vendor/upstream/spec/grammar.ebnf` on every CI
run and fails on any difference — so the keyword half of this document is
*enforced*, not merely asserted. The rest is not, and the boundary is stated
below rather than implied.

**Source of truth**, at pin `70bdd35`:

- `vendor/upstream/spec/grammar.ebnf` — `reserved_kw` for the keyword set,
  `IDENT`/`INT`/`FLOAT`/`literal` for identifiers and numbers.
- `upstream/spec/01-grammar.md` §1.2, §1.5, §3.2, §6 — comments, string forms,
  and the operator climb.
- `upstream/crates/wolf_fmt/src/{lib.rs,doc.rs}` — `STYLE_VERSION = "1"`,
  `INDENT = 4`, `WIDTH = 100`, which are `ftplugin/wolf.lua`'s numbers.

**The extraction gap ls02 recorded still stands at this pin.** `grammar.ebnf`
is generated by `wolf xtask spec-extract`, and the extraction elides the
precedence climb — the file says so itself. The quoted terminals it carries are
missing `==` `!=` `<` `>` `<=` `>=` `<=>` `&&` `||` `<<` `>>` `/` `&`; only
`spec/01-grammar.md` §3.2 has them, and that file is not vendored. So the
automated drift check covers the **keyword set only**, and an operator change
upstream is invisible to it. `nvim-check`'s doc comment says so in those words,
because a check that appears to cover more than it does is worse than one that
covers less.

Two ways out, both upstream: teach `spec-extract` to emit the climb, or vendor
§3.2's table alongside `grammar.ebnf` and have the drift check read it.

## Keywords — the closed set of 50 `[gram.inv.kw]`

Verbatim from `reserved_kw`, and the count is the spec's own checksum:

```
as asm assume borrow break comptime const continue copy defer distinct dyn
else enum errdefer export extern false fn for freeze handle if impl import in
let loop match move mut proc pub region return scope select shared spawn
struct take trait true type unsafe use var weak when while
```

In `syntax/wolf.vim` these are split across seven `syn keyword` groups —
`wolfBoolean`, `wolfConditional`, `wolfRepeat`, `wolfStatement`,
`wolfStorageClass`, `wolfStructure`, `wolfKeyword` — purely so the default
colour scheme distinguishes them. **The split is cosmetic and the union is the
claim**, which is exactly what the drift check compares: it reads every
`syn keyword` line between the `reserved-kw-begin` / `reserved-kw-end` markers,
unions the tokens, and requires set equality with `reserved_kw`. Moving a
keyword between groups is free; adding or dropping one fails CI.

The markers exist because the alternative — scanning the whole file for
`syn keyword` — would sweep up `wolfType`, whose four names are *not* reserved
keywords and must not be.

**Contextual keywords are excluded** (`[gram.inv.ctx]`): `c`, `rc`, `pool`,
`from`, `timeout`, `noalias`, `pkg`, `reg`, `self`, and the asm operand
directions. Each is an ordinary identifier everywhere except one position, and
Vim's `syn keyword` cannot see position. Painting `from` and `timeout` as
keywords would be wrong far more often than right.

`self` is the one that tempts hardest, since it appears in every method
signature the language has. It is still an identifier, and colouring it would
also colour `self` as a field name, a parameter and a local — three places it
means nothing special.

## Types

```
bool int str Self
```

Small, and deliberately so. Wolf has **no fixed-width scalar inventory at this
pin**: `i32`/`u64`/`f64` and friends appear in neither `grammar.ebnf` nor any
`spec/*.md`. Every name above is one the pinned spec or corpus actually
contains. Guessing the rest would be inventing language surface in an editor
file, which is how a highlighter ends up teaching people a language that does
not exist.

`type` and `region` are also type-level (`type ::= … | 'type' | 'region'`) but
they are reserved keywords, so they are already in the set above.

## Comments

| form | group | why |
|------|-------|-----|
| `//` | `wolfComment` | `[gram.lex.comment]` |
| `///` `//!` | `wolfDocComment` | outer and inner doc comments; matched FIRST, because `syn match` takes the earliest-defined rule and `//` would otherwise swallow both |
| *(none)* | — | **wolf has no block comment**: "nesting arguments lose to simplicity + lexer speed". There is no `/* */` region in the file, and adding one would highlight a construct the lexer rejects |

`commentstring` is `// %s` with no alternative form, and `comments` is
`:///,://!,://` — longest first, so `gq` on a doc comment does not re-flow it
as a plain one.

## Strings

Four forms, and **order matters** exactly as it does in facsimile's table:

| form | rule | note |
|------|------|------|
| `"""…"""` | `wolfBlockString` | defined **before** `"…"`, or the opening fence lexes as an empty string followed by a string start. Dedented by the closing delimiter's column |
| `r#"…"#` | `wolfRawString` | fences balance by count; Vim's regex has no counting construct, so `r"`, `r#"`, `r##"`, `r###"` are enumerated longest-first. Four `#` and beyond are not matched |
| `re"…"` | `wolfGeneralized` | an identifier fused to a string. The prefix is part of the literal so it colours as one thing; `re` alone would read as a variable |
| `"…"` | `wolfString` | the base form |

**Every string literal is an f-string** (D26/X9): `{x}` re-enters token mode
inside it, and `{{`/`}}` are the escapes. `wolfInterp` matches `{[^{}]*}` and
`wolfInterpEscape` matches the doubled braces first, so an escaped brace never
opens an interpolation. `wolfFormatSpec` colours the `:>3` in `{words:>3}`.

There is **no character literal** in wolf, so there is no single-quote rule —
which also means an apostrophe in a comment cannot start an unterminated
region, a class of bug this file simply does not have.

## Numbers

`INT ::= DEC_LIT | '0x'… | '0o'… | '0b'…` and
`FLOAT ::= DEC_LIT '.' DEC_LIT EXPONENT? | DEC_LIT EXPONENT`, each with `_`
separators. Four `syn match` rules, hex/octal/binary before decimal so `0x1f`
does not lex as `0` followed by an identifier.

## Operators

```
<=>  <<=  >>=  ..=
==  !=  <=  >=  &&  ||  <<  >>  ..  ->  =>  +=  -=  *=  /=  %=  &=  |=  ^=
+  -  *  /  %  &  |  ^  !  <  >  =  ?  @
```

**Ordering matters here, unlike in facsimile.** Vim's `syn match` is
longest-match *within one pattern* but first-match *across patterns*, so the
three-character forms are in their own alternation, defined first; otherwise
`<=>` colours as `<=` followed by a stray `>`.

All of them share one group. `^` carries two jobs (bitwise xor, and D25's
from-end index marker `s[^1]`) and `!` three (prefix not, the `!T` error-union
type, and `!=`) — a highlighter that only colours them does not have to tell
them apart.

## Identifiers, and what `iskeyword` cannot say

`IDENT ::= ('_' XID_Continue+) | (XID_Start XID_Continue*)`.

`ftplugin/wolf.lua` sets `iskeyword=@,48-57,_,192-255`, which is the closest
expressible superset: Vim's `iskeyword` is a byte/range list and cannot express
XID beyond latin-1. An identifier using a CJK or Greek `XID_Start` still
*highlights* (the syntax patterns use `\h\w*` and `\k`), but `w` and `*`
motions clip it. That is a Neovim limit rather than a wolf one, and it is
written down here rather than papered over.

## What the file cannot express

Three real parts of wolf lexical structure are out of reach for a regex
highlighter. None is a reason to add a shim — they are the argument for
semantic tokens whenever the compiler ships them (post-v1):

1. **Expressions inside interpolations.** `{x.method(1)}` colours as one unit.
   Re-entering the expression grammar is not something `syn match` can do, and
   pretending otherwise produces confident wrong colours on nested braces.
2. **Generalized-literal bodies.** `re"[a-z]+"` colours as a string with a
   `PreProc` prefix; the regex inside is not highlighted as a regex. The
   tree-sitter `injections.scm` is where that belongs, once a grammar exists.
3. **Deeply-fenced raw strings.** `r####"…"####` and beyond are not matched.
   Nothing in the corpus at this pin uses more than one `#`.

Attributes (`#[…]`) are a bounded region rather than a line directive: wolf has
no preprocessor, so `#` must not swallow the rest of the line. facsimile's
table records the same trap from the other direction (`has_preprocessor` set
`.true.` would do exactly that).
