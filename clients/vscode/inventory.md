# The wolf token inventory `syntaxes/wolf.tmLanguage.json` is generated from

This is the fourth such table in this repo — `clients/fackr/inventory.md`
(Rust), `clients/facsimile/inventory.md` (Fortran) and
`clients/nvim/inventory.md` (Vim) record the same inventory in different target
languages — and the repetition is the point: four independently-written tables
from one pinned grammar cross-check the extraction, and a drift in one is a
drift in all four.

**This one differs from the other three in a way worth stating up front: the
grammar file is not written by a human at all.** The others are hand-authored
artifacts with a check pointed at them. Here, `cargo xtask grammar-generate`
emits the entire `.tmLanguage.json`, and `cargo xtask grammar-drift`
regenerates it and compares **bytes**.

The reason is the file itself. ls04's `syntax/wolf.vim` is readable at a glance,
so comparing its `syn keyword` lines against `reserved_kw` catches what matters.
A `.tmLanguage.json` is two hundred lines of escaped regex, and a hand-edit in
the middle of one — a tightened pattern, a "fixed" scope name — is invisible to
any check that only inspects the terminal lists. Diffing generated bytes makes a
hand-edit *be* the drift, which is what ls05 §2 asks for in those words.

**Source of truth**, at pin `70bdd35`:

- `vendor/upstream/spec/grammar.ebnf` — `reserved_kw` for the keyword set, and
  every other quoted terminal for the operator inventory.
- `vendor/upstream/PIN` — `src/pin.ts`.
- `upstream/crates/wolf_fmt/src/lib.rs` — `INDENT = 4`, `WIDTH = 100`, which are
  `language-configuration.json`'s numbers.
- `upstream/crates/wolf_diag/src/{lib.rs,render.rs}` — `Severity` is exactly
  `{error, warning}` and every diagnostic carries a code, which is what the
  `$wolf` problem matcher's two patterns encode.

## What is derived, and what is not

| part | derived from the EBNF? | enforced by `grammar-drift`? |
|------|------------------------|------------------------------|
| the 50 reserved keywords | **yes**, from `reserved_kw` | yes |
| the operator inventory | **yes**, from every other quoted terminal | yes |
| which scope each keyword gets | no — a table in `xtask/src/vscode.rs` | yes (byte diff) |
| comment / string / number / interpolation structure | no — hand-written scope structure | yes (byte diff) |
| the type names | **no**, and not derivable — see below | yes (byte diff) only |

The last row is the one leak, and it is the same leak ls04 has. The
fixed-width scalar inventory is **real at pin 75fd2d0** (v0.2.1; re-read at
le04, `BUILTIN_TYPES` byte-identical across `83f83bb..v0.2.1`): spec/10 (types, D54)
writes `f32`/`f64`/`i32`/`u8` normatively, and the painted set is the
compiler's closed `BUILTIN_TYPES` — fifteen scalars, `char` (s121, D58, a
builtin since this pin) and the `wrapping` constructor (D56) — with `Self`
beside them. The EBNF still has no rule
listing type names, so a type added upstream will not appear here on its own;
`TYPE_NAMES` in `xtask/src/vscode.rs` is re-read against
`wolf_sema/src/prelude.rs` at each pin. (Through 70bdd35 the list was four
names, because no `spec/*.md` then named a fixed-width scalar.)

## THE OPERATOR GAP — closed at pin f9ee9aa

Through the `70bdd35` pin, `wolf xtask spec-extract` **elided the precedence
climb** — the extracted `grammar.ebnf` said so itself — so the quoted
terminals it carried were missing:

```
==  !=  <  >  <=  >=  <=>  &&  ||  <<  >>  /  &
```

Only `spec/01-grammar.md` §3.2 had them, and that file is not vendored. ls02
and ls04 recorded the gap; ls05 was the first to *feel* it, because ls04's Vim
file was hand-written (and quietly added the thirteen) while this grammar is
generated and reaches no further than its stated input. The visible symptom,
preserved in the pre-f9ee9aa history of `src/test/snapshots/strings.lu.txt`:
`==` rendered as **two adjacent assignment operators** and `&&` as unscoped
text.

Both remedies were upstream, and upstream took the first: at f9ee9aa the
extraction renders the full climb (tiers 3–13, spec `[gram.expr.prec]`) into
`grammar.ebnf`, the thirteen are ordinary quoted terminals, and they highlight.
The tripwire that guarded the gap
(`the_elided_precedence_climb_is_still_absent_at_this_pin`) is inverted into
`the_precedence_climb_operators_stay_in_the_vendored_ebnf`, which fails on any
pin where they vanish again.

## Keywords — the closed set of 50 `[gram.inv.kw]`

Verbatim from `reserved_kw`, and the count is the spec's own checksum:

```
as asm assume borrow break comptime const continue copy defer distinct dyn
else enum errdefer export extern false fn for freeze handle if impl import in
let loop match move mut proc pub region return scope select shared spawn
struct take trait true type unsafe use var weak when while
```

They are split across nine TextMate scopes purely so an untuned theme
distinguishes them. **The split is cosmetic and the union is the claim** — the
same sentence `clients/nvim/inventory.md` makes about its seven `syn keyword`
groups, and here it is a property of the generator rather than of anyone's
discipline: the scope lists are *filtered* by the derived set, and a test
asserts the union is exactly `reserved_kw`.

| scope | keywords |
|-------|----------|
| `constant.language.wolf` | `false` `true` |
| `keyword.control.conditional.wolf` | `else` `if` `match` |
| `keyword.control.repeat.wolf` | `for` `in` `loop` `while` |
| `keyword.control.flow.wolf` | `break` `continue` `defer` `errdefer` `return` |
| `keyword.control.import.wolf` | `import` `use` |
| `keyword.control.concurrency.wolf` | `borrow` `freeze` `move` `proc` `region` `scope` `select` `spawn` `when` |
| `storage.type.wolf` | `const` `enum` `fn` `impl` `let` `struct` `trait` `type` `var` |
| `storage.modifier.wolf` | `asm` `assume` `comptime` `copy` `distinct` `dyn` `export` `extern` `handle` `mut` `pub` `shared` `take` `unsafe` `weak` |
| `keyword.other.wolf` | `as` |

**A keyword upstream adds that this table has never heard of still reaches the
user's editor**, in `keyword.other.wolf`, and still shows as drift. That
ordering matters: ls05 §2's stated goal is that a new keyword cannot reach a
user "a release late", so the default is to colour it and make someone review
the scope, not to refuse to generate.

**Contextual keywords are excluded** (`[gram.inv.ctx]`). The EBNF carries these
word terminals that are *not* in `reserved_kw`:

```
E  _  c  e  from  inout  lateout  noalias  out  pkg  pool  rc  self  timeout
```

Each is an ordinary identifier everywhere except one position, and a TextMate
`match` cannot see position. `self` tempts hardest, since it appears in every
method signature the language has; colouring it would also colour `self` as a
field name, a parameter and a local. `E`, `e` and `_` are there for a different
reason — they are fragments of `EXPONENT` and `closed_pattern`, matched by the
numeric rules rather than as words.

That list is **machine-checked and exhaustive**: generation *fails* when a word
terminal appears in neither it nor `reserved_kw`. A contextual keyword added
upstream (`sync`, say) therefore forces a human decision instead of silently
becoming neither. This is stricter than ls04's equivalent, which lists its
contextual set in prose only — and it already found that ls04's list names
`reg`, which is not a terminal in the pinned grammar.

## Operators — what the EBNF does carry

Twenty-three, emitted **longest-first** because a TextMate alternation is
first-match, not longest-match — `..` listed before `..=` would colour `..=` as
a range followed by a stray `=`:

```
<<=  >>=  ..=
%=  &=  *=  +=  -=  ->  ..  /=  =>  ^=  |=
!  *  +  -  =  ?  @  ^  |
```

The eleven of `assign_op` are all present. What is missing is §3.2's, above.

Delimiters and literal fragments are excluded by name in
`xtask/src/vscode.rs`'s `DELIMITERS`: `"` `#[` `(` `)` `,` `.` `:` `[` `]` `{`
`}` `{{` `}}` `0b` `0o` `0x`. Everything symbolic that is *not* on that list
becomes an operator, so a symbol added upstream highlights immediately — an
uncoloured new operator is a smaller wrong than a silent one.

## Comments

| form | scope | why |
|------|-------|-----|
| `///` `//!` | `comment.line.documentation.wolf` | matched **first**, because the earliest-listed rule wins and `//` would otherwise swallow both |
| `//` | `comment.line.double-slash.wolf` | `[gram.lex.comment]` |
| *(none)* | — | **wolf has no block comment**: "nesting arguments lose to simplicity + lexer speed". `language-configuration.json` has no `blockComment` key, so `editor.action.blockComment` does nothing rather than emitting a construct the lexer rejects |

## Strings

Four forms, and **order matters** exactly as it does in the other three tables:

| form | scope | note |
|------|-------|------|
| `"""…"""` | `string.quoted.triple.wolf` | defined **before** `"…"`, or the opening fence lexes as an empty string followed by a string start |
| `r#"…"#` | `string.quoted.other.raw.wolf` | see below |
| `re"…"` | `string.quoted.other.generalized.wolf` | an identifier fused to a string; the prefix carries `support.function.generalized.wolf` so it colours as one thing. Adjacency is required, which is what keeps `extern "C"` — keyword, space, string — out of this rule |
| `"…"` | `string.quoted.double.wolf` | the base form |

**Raw strings are the one place TextMate beats the Vim file.**
`clients/nvim/inventory.md` has to enumerate `r"`, `r#"`, `r##"`, `r###"` and
gives up past three, because Vim's regex has no counting construct. TextMate's
`begin`/`end` pair supports a backreference, so `begin: "\\br(#*)\"", end:
"\"\\1"` balances the fence **by count, to any depth**. ls04's limitation #3
simply does not exist here.

**Every string literal is an f-string** (D26/X9), which is why `#interpolation`
is included from all four forms rather than from the plain one. `{{` and `}}`
are matched *first*, so a doubled brace never opens an interpolation, and
`constant.other.format-spec.wolf` colours the `:>3` in `{words:>3}`.

There is **no character literal** in wolf, so there is no single-quote rule —
which also means an apostrophe in a comment cannot open an unterminated string,
a class of bug this file does not have. For the same reason
`language-configuration.json` auto-closes no single quote.

## Numbers

`INT ::= DEC_LIT | '0x'… | '0o'… | '0b'…` and `FLOAT ::= DEC_LIT '.' DEC_LIT
EXPONENT? | DEC_LIT EXPONENT`, each with `_` separators. Five rules, radix forms
and float before decimal so `0x1f` does not lex as `0` followed by an
identifier.

## Identifiers, and what VS Code gets for free

`IDENT ::= ('_' XID_Continue+) | (XID_Start XID_Continue*)`.

`language-configuration.json` sets **no** `wordPattern`, and does not need one:
VS Code's default already selects unicode identifiers. The limitation ls04 had
to write down — Vim's `iskeyword` is a byte/range list that cannot express XID
beyond latin-1, so `w` motions clip a CJK or Greek identifier — does not exist
in this editor.

## What the grammar still cannot express

Two, down from ls04's three (raw-string fences being the one TextMate solves).
Neither is a reason to add a shim; both are the argument for semantic tokens
whenever the compiler ships them (post-v1):

1. **Expressions inside interpolations.** `{x.method(1)}` gets an embedded
   scope and its keywords, numbers, types and operators are re-scanned, but it
   is not the expression grammar — nested braces inside an interpolation end it
   early. Re-entering a real grammar is not something a TextMate rule can do.
2. **Generalized-literal bodies.** `re"[a-z]+"` colours as a string with a
   distinct prefix; the regex inside is not highlighted as a regex. A tree-sitter
   `injections.scm` is where that belongs, and VS Code would need the grammar to
   declare an embedded scope for a language it does not have.

Attributes (`#[…]`) are a bounded region rather than a line directive: wolf has
no preprocessor, so `#` must not swallow the rest of the line.
`clients/facsimile/inventory.md` records the same trap from the other direction.

## One extraction hazard, recorded because it nearly shipped

`grammar.ebnf` mixes prose comments with quoted terminals, and prose contains
apostrophes. Line 34 is:

```
ret_type  ::= type ('!' error_row)?   /* `-> !T` parses via type's '!' type */
```

Pairing quotes naively across that line yields the "terminals" `s ` and
` type */`, and a generator that swallowed those would emit them into a user's
editor as language surface. The extraction therefore strips `/* … */` (which may
span lines) and the `#` header *before* scanning, and a unit test —
`prose_apostrophes_are_not_mistaken_for_terminals` — pins the exact line.

That the word terminals then partition **exactly** into `reserved_kw` and the
contextual list is the independent confirmation that the strip is complete.
