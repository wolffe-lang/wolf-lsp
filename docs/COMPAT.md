# Compatibility — which `wolf` each client works with

> **NOTHING HERE HAS BEEN PUBLISHED.** wolf is pre-release in private
> repositories, the VS Code publisher identity is unregistered, and `wolf-lang`
> has no tagged release. Every distribution channel in this repository is built,
> dry-run proven and switched **off**; the steps that would cross a network are
> human-gated and listed in [`DISTRIBUTION.md`](DISTRIBUTION.md). The table
> below therefore describes what a client *would* declare at its first release,
> and nobody has installed any of it from anywhere.

Editor tooling rots by drifting silently out of compatibility with its server.
This file, `clients/*/compat.json` and the runtime check in the two clients that
can carry one are the machinery that makes that drift loud instead.

## The claim, and its exact width

Client versions are the **client's**, not wolf's (ls07 non-target: no
version-lockstep). What each client owes is a declared range of `wolf` it works
with, and the rule that governs the range is one sentence:

> **`max_tested` may only name a wolf version this repository has actually run
> the conformance suite against.**

That rule is a gate, not a convention. `cargo xtask compat-check` derives the
*earned set* from `vendor/upstream/PIN` and fails if any client declares a
`max_tested` outside it — and it runs in `cargo xtask ci`, on every push, so the
moment a range outruns its evidence is the moment somebody edits the file rather
than the moment somebody tags a release.

**Today the earned set has exactly one member.** `wolf-lang` publishes no
releases; this repository pins one commit, `wolf --version` at that commit
prints one string, and every transcript under `transcripts/` was recorded
against it. So the schema supports ranges and the data claims a point. Widening
`max_tested` to a version nobody has run turns the build red, which was tested
deliberately — see *The red test*, below.

## Pre-1.0 posture, stated plainly

Until wolf v1 the range below is a **pin range**, not a stability promise.
Breakage between compiler campaigns is *expected*: `wolf lsp` is being built at
the same time as these clients, and a campaign that changes a diagnostic code, a
capability, or a position-encoding preference can move the wire under a client
that did nothing wrong. The honest posture is to say so here rather than to
imply a stability this track cannot provide.

That is also why no client refuses to run out of range. An out-of-range server
usually mostly works, and blocking a user's editor is worse than warning them.

## The schema

`clients/<client>/compat.json`, validated by `cargo xtask compat-check`:

| key | meaning |
|---|---|
| `client` | the artifact's own name, as a user would see it |
| `client_version` | this client's version — cross-checked against `package.json` / `extension.toml` / `Cargo.toml` where one exists |
| `artifact` | what actually ships, and from where |
| `wolf.min` | the oldest wolf this client claims to work with |
| `wolf.max_tested` | the newest wolf the suite has been run against. **Earned only** |
| `wolf.pin` | the commit `vendor/upstream/PIN` names; must agree |
| `wolf.pin_version_string` | the exact `wolf --version` output at that commit |
| `verified.date` | ISO date of the run that earned `max_tested` |
| `verified.host` | where it ran — a single-host run is not a D35 three-OS claim |
| `verified.evidence` | transcripts, profiles and suites; repo-relative paths are checked for existence |
| `verified.caveat` | optional, and used where the row is weaker than it looks (Zed) |
| `warning_surface` | where the runtime mismatch message appears, or why there is none |

### Which clients have one, and which deliberately do not

`fackr`, `facsimile` and `jetbrains` carry no `compat.json`, and
`compat-check` fails if one appears. The reason is structural: a compatibility
range describes a *release*, and none of the three is a release this repository
cuts. fackr's and facsimile's deliverable is a patch series applied to somebody
else's editor — the range statement travels with the patch, into their
repository, under their version scheme — and `jetbrains/` is a page of prose
with no artefact at all.

## The runtime check

Each client that can run code compares `wolf --version` against its declared
range at startup and, on a mismatch, emits **exactly one** actionable message
naming both versions and what to do. No modal, no repetition, no auto-update,
no refusal to run.

| client | surface | behaviour |
|---|---|---|
| Neovim | `:checkhealth wolf` | a `warn` naming both versions, the range, and the fix ladder. `plugin_spec.lua` drives it against a stand-in binary written at runtime, so the message is asserted rather than assumed |
| VS Code | one notification at activation + `Wolf: Show Version` | fires at most once per session (module-level latch), non-modal, two buttons: the install page and the output channel. The server starts either way |
| Helix | none | a TOML fragment cannot run code. This file is the whole statement |
| Emacs | none | `wolf-mode.el` is a copy-pasteable snippet, and a snippet that phones a version check is a snippet nobody pastes |
| Zed | none | the extension's only wasm entry point is `language_server_command`, which Zed calls before there is anywhere to raise a notification |
| fackr / facsimile | their own log surfaces | **owed to the patch series, not shipped here.** Both patch sets predate this file and neither carries a version comparison; adding one is a change to somebody else's editor and belongs in a follow-up PR to each. Recorded in [`UPSTREAM.md`](UPSTREAM.md) |

The two implemented checks share one shape: parse the leading
`MAJOR.MINOR.PATCH` out of `wolf --version`, compare numerically against
`[min, max_tested]`, say which side of the range the binary is on, and get out
of the way. Numerically matters — `0.10.0 < 0.9.0` as strings, and a unit test
in `xtask/src/compat.rs` pins the ordering.

## The red test

ls07's acceptance asks for the refusal to be *exercised*, not asserted. It was:

```
$ # clients/vscode/compat.json, max_tested 0.0.1 -> 0.1.0
$ cargo xtask compat-check
compat-check: clients/vscode/compat.json: `wolf.max_tested` is "0.1.0", which the suite
has never been run against. Earned versions today: 0.0.1. …
compat-check: 1 problem(s)
$ # reverted; green again
```

The same command is red for a `pin` that disagrees with `vendor/upstream/PIN`,
for a `client_version` that disagrees with `package.json`, for an empty range,
for a `verified.evidence` entry naming a file that does not exist, and for a
hand edit to either generated artifact.
