## 3. Prediction, committed before the pin moves

Written 2026-09-24 with `vendor/upstream/PIN` still at `2e4ca769`, before any
re-vendor, any re-record, and before `type-names-check` was run against an
acquired 0.2.16 binary.

**On honesty about what is a prediction here.** The contract's §2 ordered the
anchor key-set diff as an INPUT — "first act" — so the 15/0/0 above is a
measurement already made, not a forecast, and it is written as such. §3's other
three items are forecasts, each with its falsifier.

### (i) `TYPE_NAMES` does not move, and the gate that says so is blind

**Predicted: `TYPE_NAMES` is unchanged, and `cargo xtask type-names-check
--require-server` passes at 0.2.16 with no new classification row.**

The gate's candidate set is the **second segment of every `type.*` anchor**
(`xtask/src/type_names.rs::type_anchor_segments`). Diffed both ways across the
two tags it is **18 words on each side with zero added and zero dropped** —
`byte char closure comb err float fn generic interp list map method numlit
range row str trait unit`. The one new `type.*` anchor is
`type.err.alias.qualified`, whose second segment `err` was already in the set
at 0.2.15. So the gate asks the 0.2.16 binary exactly the questions it asked
the 0.2.15 one.

**Falsifier:** any word in the candidate set at one tag and not the other, or
any red out of `type-names-check`.

**And the finding I expect this to produce, which is the opposite of a
nuisance.** `prelude.rs` gains **two real type names** at this pin — `Scope`
and `Proc` — the first prelude NAMES added since s158's `range`. `fn
fan_out(s: Scope)` and `fn watch(p: Proc[int])` are programs at 0.2.16 and were
`error[E0301]` at 0.2.15. The gate cannot see either of them, because their
clauses are anchored `conc.proc.handle` and `[conc.task.scope]` — **`conc.*`,
not `type.*`** — and the candidate set is the spec's `type.` index. This is
precisely the first bullet of `type_names.rs`'s own "What the gate cannot see":
*a builtin added upstream without a two-segment `type.<name>` anchor of its own
spelling*. That paragraph has been a hypothetical since wolf-lsp#24 was
written. **Predicted: at this pin it becomes live for the first time, and the
gate stays green while the set it guards is two names short.** A green gate
that cannot go red for the case that just occurred is the shape wave 45 spent a
whole directive naming, so it is filed rather than absorbed.

**Falsifier:** if the acquired 0.2.16 binary answers `E0301` to `Scope` in type
position, the names did not land as the CHANGELOG says and there is no hole.

### (ii) The scripted transcripts: how many move beyond their header

`crates/wolf_query/` **and** `crates/wolf_lsp/` are **both byte-identical**
across `2e4ca769..93a5fe50` — `git diff --stat` is empty for each. At the last
bump that fact was the whole of tl09's prediction and tl09 was wrong, because
the semantic-token walk's input is the whole compiler. 148 commits and 125
changed files land here against the 162 and the one-file query span that moved
last time, so the same reasoning cannot simply be repeated louder.

**Predicted: 0 of 71 move beyond the header** — 71 files changed, header-only
(`wolf_pin` and `recorded`, line 1), 0 body diffs.

The prediction is made by walking the release's landed changes against the
**fifteen vendored sample documents the 71 scripts actually open**, rather than
against the diffstat:

- **#444 (`move` of a `Copy` place is E1001)** — the biggest behaviour change in
  the release. Not one of the fifteen samples uses the `move` operator;
  `regions.lu:36` carries the word only in a comment. No document gains a
  diagnostic.
- **#312 (`spawn proc` shares frozen data)** — no sample spawns anything.
- **#316 / `[conc.proc.join]` (`Scope`, `Proc[T]`, `p.join()`)** — no sample
  names a handle type, so no hover, inlay hint or completion detail can print
  one.
- **#400 (a call through a fn-typed parameter)** — no sample has a fn-typed
  parameter.
- **#391/#392 (the checked tier's `str` producers charge the region)** — a
  runtime charging fact; nothing the server reports about a document.
- **`[conf.exit]` (a rejected program exits 2, a refusal 4)** — the loudest
  trap in this release for a downstream, and it does not reach this repository:
  nothing here reads `wolf build`'s exit code. `type_names.rs` classifies on
  **stderr** (`verdict_from_stderr`), `onetruth` compares diagnostics
  positionally, and `doctor` only calls `--version`, which exits 0 whatever the
  program. Grepped for `status.code`, `success()` and `exit_code` across
  `crates/`, `src/`, `tests/` and `xtask/`: 17 hits, none of them an expectation
  about a compile of a `fail(...)` sample.
- **`[type.list.lit.elem]`** — the notes say it in as many words: *"No compiler
  change."* `strings/bytes_roundtrip.lu`'s `List[byte]` hover does not move.
- **`[mem.str.ws]` (`trim` takes no argument)** — ruled FOR THE SPEC; wolf
  changes nothing.

**Where I expect to be wrong, if I am.** Two named candidates, in order:

1. **`annotate/semanticTokens-error`.** s175 (#434) rewrote error-row entry
   resolution wholesale — "the row lowering only ever looked up a single-segment
   path in the current module; it now resolves an entry the way a type path
   resolves" — and put the resolver's **reference table** through the new path.
   That reference table is exactly the machinery s165 moved last release, and
   moving it is exactly what painted `IoErrors` and `ConfigErrors` where they
   are USED. `rows/error_alias_union.lu`'s entries are single-segment and
   same-module, which is the case #434 says it preserves; if the rewrite is not
   a strict extension, this transcript is where it shows, for the second bump
   running.
2. **`requests/document-symbol` and `requests/hover-nothing-there`**, both on
   `errors.lu` — which carries the **only qualified row entry in the vendored
   sample set**, `io.Error`, at lines 25 and 38. #434 is about exactly that
   shape. `io` is bound to no module in that file, so under the new rule the
   entry should fall through to "everything else is a tag" and stay a tag; if
   it does not, `errors.lu` gains a resolve diagnostic and both transcripts
   move at their `wait diagnostics` step.

**Falsifier:** any non-header hunk in any of the 71. If one moves, it is named,
its coordinates are given, and it is explained by a landed clause — or, failing
that, filed as a finding and NOT silently re-recorded.
