## 3. Prediction, committed before the pin moves

Written 2026-09-24 with `vendor/upstream/PIN` still at `2e4ca769`, before any
re-vendor, any re-record, and before `type-names-check` was run against an
acquired 0.2.16 binary.

**On honesty about what is a prediction here.** The contract's §2 ordered the
anchor key-set diff as an INPUT — "first act" — so the 15/0/0 above is a
measurement already made, not a forecast, and it is written as such. §3's other
three items are forecasts, each with its falsifier.

### (i) `TYPE_NAMES` does not move, and the gate that says so is blind

**Predicted: `TYPE_NAMES` is unchanged, and `cargo xtask type-names-check
--require-server` passes at 0.2.16 with no new classification row.**

The gate's candidate set is the **second segment of every `type.*` anchor**
(`xtask/src/type_names.rs::type_anchor_segments`). Diffed both ways across the
two tags it is **18 words on each side with zero added and zero dropped** —
`byte char closure comb err float fn generic interp list map method numlit
range row str trait unit`. The one new `type.*` anchor is
`type.err.alias.qualified`, whose second segment `err` was already in the set
at 0.2.15. So the gate asks the 0.2.16 binary exactly the questions it asked
the 0.2.15 one.

**Falsifier:** any word in the candidate set at one tag and not the other, or
any red out of `type-names-check`.

**And the finding I expect this to produce, which is the opposite of a
nuisance.** `prelude.rs` gains **two real type names** at this pin — `Scope`
and `Proc` — the first prelude NAMES added since s158's `range`. `fn
fan_out(s: Scope)` and `fn watch(p: Proc[int])` are programs at 0.2.16 and were
`error[E0301]` at 0.2.15. The gate cannot see either of them, because their
clauses are anchored `conc.proc.handle` and `[conc.task.scope]` — **`conc.*`,
not `type.*`** — and the candidate set is the spec's `type.` index. This is
precisely the first bullet of `type_names.rs`'s own "What the gate cannot see":
*a builtin added upstream without a two-segment `type.<name>` anchor of its own
spelling*. That paragraph has been a hypothetical since wolf-lsp#24 was
written. **Predicted: at this pin it becomes live for the first time, and the
gate stays green while the set it guards is two names short.** A green gate
that cannot go red for the case that just occurred is the shape wave 45 spent a
whole directive naming, so it is filed rather than absorbed.

**Falsifier:** if the acquired 0.2.16 binary answers `E0301` to `Scope` in type
position, the names did not land as the CHANGELOG says and there is no hole.

**Predicted: 0 of 71 move beyond the header** — 71 files changed, header-only

The prediction is made by walking the release's landed changes against the

### The transcript prediction, and why it failed

The re-record: `71 files changed, 72 insertions(+), 72 deletions(-)`. Seventy
are header-only. The seventy-first is `requests/formatting-byte-stable`, whose
one further changed line is a **`c2s` `textDocument/didOpen`** — the client's
own payload — carrying the re-vendored `regions.lu` with `phase: mem` become
`phase: run` (wolf-lang `ac256b20`, s170). The formatting **response** did not
move. Classified by `dir`, **zero `s2c` lines changed in the entire library**.

The prediction walked every landed behaviour change in the release against the
fifteen sample documents — #444's `move`, #312's spawn, #316's handles, #400's
fn-typed parameter, #391/#392's region charging, `[conf.exit]`,
`[type.list.lit.elem]`, `[mem.str.ws]` — and **every one of those calls was
correct**. It never checked whether the vendored inputs had moved. tl09
measured that explicitly ("fifteen blob-sha pairs, fifteen matches"); this lane
assumed it, and the one thing that moved is the one thing nobody looked at.

**The rule that comes out of it, for the next bump: a pin bump has two
independent sources of transcript movement — what the server answers, and what
the vendored documents say — and a prediction about one is not a prediction
about the other.** 0.2.15 moved the first and not the second; 0.2.16 moved the
second and not the first. Both named fallback candidates held, which is its own
answer: wolf-lang#434 is a strict extension on the same-module single-segment
row entry, and an unresolvable `io.` prefix still falls through to a tag.

### THE FINDING: the type-names gate is green and blind, and this is the first pin at which that matters

`crates/wolf_sema/src/prelude.rs` gains `Scope` and `Proc` at v0.2.16 — the
first prelude TYPE NAMES added since s158's `range`. `xtask type-names-check`
cannot see either, and passes.

**Why.** The gate's candidate set is the **second segment of every `type.*`
anchor** in the vendored `spec/anchors.json`
(`xtask/src/type_names.rs::type_anchor_segments`). `Scope` and `Proc` are
anchored `[conc.task.scope]` and `[conc.proc.handle]` — `conc.*`. Diffed both
ways, the candidate set is **18 words at 2e4ca769 and 18 at 93a5fe50, zero
added, zero dropped**.

**Proved, not asserted.** The gate's own probe source, byte-identical, run
against both acquired release binaries:

```
Scope        0.2.15: NotAName  (E0301)    0.2.16: Name (resolves in type position)
Proc         0.2.15: NotAName  (E0301)    0.2.16: Name
Proc[int]    0.2.15: NotAName  (E0301)    0.2.16: Name
Pool         0.2.15: Name                 0.2.16: Name     (control, unmoved)
Mutex        0.2.15: Name                 0.2.16: Name     (control, unmoved)
range        0.2.15: Name                 0.2.16: Name     (control, unmoved)
int          0.2.15: Name                 0.2.16: Name     (control, unmoved)
```

verbatim at 0.2.15: `error[E0301]: nothing named `Scope` is in scope`, and
exit 0 on the same bytes at 0.2.16.

**This is the gate's own documented blind spot going live.**
`type_names.rs`'s "What the gate cannot see" opens with *"A builtin added
upstream WITHOUT a two-segment `type.<name>` anchor of its own spelling"*. That
sentence has been a hypothetical since wolf-lsp#24 was written; v0.2.16 is the
first release that instantiates it. A gate that cannot go red for the case that
just occurred is wave-45's standing shape, and it is filed as wolf-lsp#32 rather than absorbed.

**What this lane did about it, and what it deliberately did not.**

- **Did:** classified both words by hand in `TYPE_POSITION_UNPAINTED`, with
  their reasons. That is not cosmetic — every row in that table is a name the
  gate ASSERTS still resolves at every future pin, so a removal or rename
  upstream now turns it red. Before these rows the gate had no opinion about
  either word. `type-names-check` goes 6 unpainted → **8**.
- **Did:** saw the gate red before trusting it. Planted `ScopeXYZ` in place of
  `Scope` in `TYPE_POSITION_UNPAINTED`, and the gate said, exit 1:
  `TYPE_POSITION_UNPAINTED lists \`ScopeXYZ\`, and the pinned compiler does not
  resolve it in type position (E0301, …) — a stale exclusion row`. Reverted in
  the same working tree before the commit.
- **Did NOT:** paint them. Painting `Scope` is defensible — unlike `Pool`,
  `Mutex` and `channel` it takes no argument and has no expression form — but
  it is a RULING with a five-artifact cost, and the wolf-lang corpus at this pin
  contains **zero uses of `Scope` in code** (one comment, `memory/defer_order.lu`),
  so there is no witness to test a paint against. `Proc` takes an argument and
  sits squarely under `Pool`/`Mutex`'s existing reason. Left to a lane whose
  job is rulings.
- **Did NOT:** widen the candidate set to `conc.*` or to "any capitalized
  segment". Either would be a redesign of what the spec index means to this
  gate, and doing it inside a pin bump would land an unreviewed rule change
  behind a green.

### One more false signal, this lane's own

While waiting for `cargo build` on the build host I polled with
`pgrep -f "cargo build"`. The probe's own `bash -lc` command line **contains
the string `cargo build`**, so `pgrep` matched itself and the waiter printed
`BUILDING` for twenty-eight minutes after the build had finished. Nothing was
lost but time, and the shape is the familiar one: a liveness check that cannot
return "dead" is not a liveness check. The remedy used afterwards was to ask
for the artifact (`cargo build` returning `Finished … in 0.06s`) rather than
for the process.
